# LDW Commander — Gate A Session Trust Contract (REVIEW CANDIDATE)

Status: PROPOSED / SOURCE-ONLY / INDEPENDENT SECURITY REVIEW REQUIRED
Issue: infrastructure-tools #209
Owner goal: first-party Desktop Commander replacement with **real Administrator/root capabilities** across expressly enrolled owner-controlled hosts, accessible from ordinary ChatGPT Chat and local CLI, no Work or GitHub runtime bus, no per-operation UAC, and no third-party Desktop Commander usage/quota.

This proposal does **not** grant a ChatGPT model independent authority to become Administrator/root merely by asking. It enables a powerful, short-lived, revocable **owner-authorized session**, not a permanent unauthenticated remote shell.

## 1. Distinct authority planes

- **LDW Host Agent:** host visibility and normal-user lifecycle. It does not interpret arbitrary privileged commands.
- **Existing Admin Broker (#52/#176/#185/#186):** sealed catalog of reviewed typed operations, already capable of a UAC-free elevated proof. Its protected interface remains unchanged.
- **New LDW Commander Agent (this contract):** separate protected per-host service for arbitrary terminal/files/process/service work after a session grant; never reuse the existing Hyper-V SYSTEM observer, CI/JIT protected worker or fixed-operation Admin Broker as a generic shell.
- **LDW Commander Session Authority:** validates authenticated owner/delegated operator policy and issues short-lived, host- and privilege-bound capabilities. It is not an LLM, a chat transcript, a mutable GitHub comment or a bearer passed as a chat parameter.
- **LDW Commander CLI:** local owner-side operator that does not depend on ChatGPT, Cloudflare, GitHub or third-party Desktop Commander.
- **Normal ChatGPT Chat plugin/connector:** a convenience control surface that sends bounded session operation requests through a supported authenticated private connector. Plugin availability, write approvals and actual chat-plan support must be proven; tool invocation is not privilege authority.

One canonical operation/session state per host. No second independent session broker, duplicated queue or global static admin credential.

## 2. Trust roots and enrollment

Each host must be paired independently with owner presence or an already accepted trusted enrollment proof. Enrollment records are protected locally; each binds an immutable host identifier, OS platform, pinned host public key/certificate, accepted Commander agent binary/package digest, allowed owner/operator identities, revocation epoch and expiry/rotation policy.

Do not treat a hostname, IP, Tailscale peer name, LAN presence or command-line requested target as sufficient host authentication. Pairing credentials must be per-host, not one wildcard key that compromises all machines.

Preferred transport is mutually authenticated, encrypted and private (e.g. approved overlay network or outbound authenticated relay) with pinned endpoints and separately rotated connection identities. No default public management port, unauthenticated inbound listener, copied SSH private key or raw Windows admin password in the model context.

An off-site host that cannot presently be reached returns HOST_UNAVAILABLE. The rest of the fleet must not inherit its authority or fall back to an unauthenticated transport. REDRIX/Dragonfly host enrollment remains HW&VM ORCH-owned and cannot alter its reviewed #98/#192 controls as a side effect.

## 3. Three privilege envelopes

- OBSERVE: read host status, approved process and file metadata. Never implies arbitrary secret reads.
- MAINTAIN: only owner-delegated recurring maintenance categories with reviewed operation policy and bounded parameters. May be auto-issued for previously signed host/action-scoped delegated tasks without per-command UAC; delegation has a maximum 30-day lifetime, immediate revocation support and a defined renewal ceremony, never open-ended owner approval.
- FULL_ADMIN: intentionally supports arbitrary **owner-authorized** Windows Administrator / Linux root terminal and associated file/process/service operations **within one accepted short-lived session**. Broad capability is an explicit feature, not a fixed-command-only substitute. Requesting FULL_ADMIN is a separate high-trust policy action, not inferred from general chat authority.

### FULL_ADMIN operation modes — resolve independent reviewer M1

The privilege envelope and the enforcement boundary are **separate attributes** of one signed session; the host must record and independently verify which mode was accepted.

- **FULL_ADMIN-CONFINED — disposable, secret-free VM/guest canary.** The process can be Admin/root **inside the guest** but external trusted isolation controls (host/hypervisor/network policy outside the guest's privilege) deny unapproved file mounts, external network egress and persistence. A **source-pinned fixed workload or typed reviewed operation** has a deterministic pre-spawn admission decision. Any unrecognized command, hidden child action, network target, secret/file path or conflicting policy is denied *before spawn*, and an actual external-enforcement negative test must show denied packets and no secret read/copy. This is the only mode in which the design claims enforceable exfiltration prevention.
- **FULL_ADMIN-UNRESTRICTED — real owner host, genuine arbitrary administrative operations.** This is the eventual Desktop Commander replacement capability. A verified *fresh owner-presence* authorization names the exact host/session, explicitly acknowledges that arbitrary Admin/root code may read local secrets, create durable services/tasks and use network egress, and accepts the bounded blast radius. Signed session TTL, host/owner identity, revocation, command correlation, audit and independently accepted high-impact intent gates apply. There is **no claim that a same-privilege parser can classify or prevent the egress/secrets of arbitrary scripts**. Commands inside an already accepted owner-approved batch can run without repeated UAC; genuinely new consequential intents outside that approval require a new out-of-model signed decision. A model cannot select this mode, sign consent or silently expand the accepted risk.
- **Mode confusion is fatal:** CONFINED cannot automatically downgrade/fallback to UNRESTRICTED if its sandbox, classifier or network policy is unavailable. Real-host FULL_ADMIN may never be presented as CONFINED or falsely pass its egress tests. The accepted grant binds mode, guest/host identity, exact risk text and expiry; a missing, unrecognized or widened mode returns `MODE_NOT_AUTHORIZED`.

**Review/test split:** Gate B/C/D pre-execution unknown-command/exfiltration refusal is a **CONFINED typed-canary proof**, not a promise for arbitrary shell text. Gate F real-host FULL_ADMIN is **UNRESTRICTED only after separately signed owner acceptance**, explicit uncompensated-risk disclosure and a bounded roll-back/recovery plan. Both require real OS/owner isolation evidence before any deployment; code/tests in the current drafts only exercise a non-elevated fixture.

A session grant is minted by the protected Session Authority **only after verification of a separately authenticated owner decision record or an existing signed scoped delegation**. A chat message, prompt, GitHub comment, browser page, relay tool call or role label is never owner consent. Routine pre-authorized MAINTAIN operations do not require Eddie on each action; novel destructive, customer, identity/MFA, billing, legal, DNS, public-exposure, production/risk or recovery actions preserve their existing gates. A FULL_ADMIN grant does not erase those per-action risk gates.

### Gate A1 — independently authenticated owner decision and issuance (fixes independent M1)

1. The owner decision is captured by a **separate trusted non-scriptable presence ceremony**, not by a chat transcript, same-user CLI flag, automation-clickable dialog, local agent callback or model-provided `approved=true`. Logged-in OS identity alone is **not** owner presence: a process running as the same desktop user can otherwise impersonate it. The acceptance must use a hardware- or device-backed, nonexportable signer plus a **fresh physical user-verification/presence act** (e.g. trusted security-key gesture with verification and an owner-visible confirmation on a separate trusted display/device) bound to the full transaction digest, not a silent API call. If a same-user process can simulate that gesture, approve its own transaction or substitute the displayed host/risk, the mechanism is NOT accepted and FULL_ADMIN fails closed.
2. The authorization is a **signed canonical decision record** binding operator, separately pinned owner-signer key ID/generation, issuer generation, immutable enrolled host and public key, privilege **and FULL_ADMIN mode**, one-time decision or narrow MAINTAIN delegation, accepted activity class for typed CONFINED/MAINTAIN operations or an **immutable exact executable/command/batch digest for every UNRESTRICTED operation authorized for execution**; explicitly accepted unrestricted-host secrets/egress/persistence and data-output risk, nonce, issue/expiry, session lifetime, maximum commands and human-visible intent/risk wording. MAINTAIN delegation enumerates reviewed classes/parameters/host, expires within **30 days**, is independently revocable before expiry, and requires renewed owner-presence approval; never silently promotes to FULL_ADMIN. A standing "Eddie approved everything" chat statement is not a delegation.
3. The **owner signer is a distinct trust root from the session issuer**, with an enrolled/pinned public verification key on each authorized host and the protected issuer. Its private key remains hardware-/secure-enclave-backed and unavailable to the ChatGPT connector, same-user local agent process, Commander daemon and session issuer. A signer certificate or key rotation requires an out-of-band owner-presence ceremony, explicit key ID/generation readback, host/issuer pin update and old-key revocation; compromise freezes grants and forces protected re-enrollment. The issuer verifies the independent signature, mode/identity/scope, nonce uniqueness, version, TTL, signer epoch and current revocation **before** minting; the host independently checks the signed decision digest and its locally protected mode/policy on every command. A local agent's ability to call the signing API cannot satisfy owner presence.
4. **FULL_ADMIN-UNRESTRICTED** opens only after that fresh, human-verified, non-scriptable acceptance for the exact real host/session and the unrestricted secrets/egress/persistence risk. Arbitrary commands are functionally possible inside the accepted window, but only after **each actual command belongs to a separately signed immutable owner-approved batch**; no wildcard 'any code the model later invents' grant is accepted. A new interactive command outside the signed batch must receive a fresh out-of-model owner decision before spawn; previously approved batch commands execute without repeated UAC or owner clicks. Exact-byte approval binds what starts, **not** all hidden effects of arbitrary root/Admin code; the owner-visible risk acceptance must disclose this residual risk rather than claim a script interpreter can police its nested/dynamic actions. **FULL_ADMIN-CONFINED** uses the separately attested external guest/network policy and enforceable typed-canary admission; unknown actions are refused before spawn, without falling back to unrestricted.
5. If an owner decision is absent, forged, stale, replayed, broadened, from a wrong host, from a model/tool argument or revoked, the result is `OWNER_AUTH_NOT_PROVEN`; no FULL_ADMIN session opens and no degraded implicit alternative is allowed.

**Required negative proof:** forged "Eddie approved" messages in Slack/repo/MCP/browser and a **local malicious process already running as the owner** (including automated mouse/keyboard/UI/API calls to the consent interface) cannot approve or mint a FULL_ADMIN decision without the real owner's fresh non-scriptable physical confirmation bound to the exact host/mode/risk digest. A stolen session token or a MAINTAIN delegation cannot widen host/mode/privilege; an expired or revoked owner signer, spoofed signer generation or fake owner-visible digest fails closed. A newly destructive intent outside an accepted batch requires a new signed consent. Test signer custody/rotation/revocation and the inability of a same-user agent to use the signer without the trusted presence gesture. Existing synthetic software Ed25519 test signers do **not** satisfy these requirements.

### Gate A1b — executable identity and intent/batch binding (GM18 independent M1 correction)

- For any UNRESTRICTED command, the separately signed **owner-visible batch** must identify the concrete enrolled host/session/mode and each command ID, executable identity plus immutable bytes/hash, argument vector, working directory, allowed environment keys/values or their digest, stdin content/digest where supplied, and every executable script/module/payload dependency that can be pinned. It must also display the intended file/service/process scope, persistence/egress exposure, data-output release class and unrestricted hidden-side-effect warning. A general session TTL or natural-language description is **not** an executable approval.
- The protected per-host pre-spawn verifier compares the signed canonical command/batch digest and each referenced executable artifact to the **actual bytes/parameters it will launch**. Resolve paths and reject symlink/reparse/path alias ambiguity; launch from a protected, immutable, exact-hash staging artifact or already-open verified handle so that changing a script after verification cannot substitute bytes before process start. A changed argument, stdin, environment, script module, child launch template, download, command substitution or newly requested interactive command **outside the approved batch** is refused before spawn as `COMMAND_INTENT_NOT_AUTHORIZED`, until a fresh independently signed owner decision is available.
- There is **no claim to semantically understand arbitrary shell scripts**. A signed script may dynamically run code, spawn children, install services, read secrets and egress in ways a same-privilege admission parser cannot prevent; this residual risk is disclosed and accepted explicitly for the reviewed batch/host. If the batch invokes uncontrolled remote code or other unpinned mutable execution dependencies, the verifier cannot claim exact-byte authorization and must refuse the exact-batch assurance. A future policy permitting open-ended code execution is a **separate consequential, independently reviewed owner decision**, not an implicit feature of this source proof.
- An approved batch may contain multiple different arbitrary commands and run them without per-operation UAC. Routine already signed MAINTAIN delegates remain separately bounded to their typed allowlist and 30-day maximum; they cannot be widened to arbitrary FULL_ADMIN. The signer and actual host—not the model, relay or CLI process—enforce one-time command IDs, signed batch membership, expiry/revoke, mode and concurrency.
- **Negative proof:** changed/encoded script bytes, swapped module after checking a hash, new script download, altered stdin or arguments, shell substitution, malicious same-user checkout write and prompt-injected extra command must fail **before spawn**, with verified absence of the substituted process. A trusted disposable test may separately show that an owner-approved *multiple-command* batch executes without repeat UAC, but it does not establish protection from opaque nested side effects on an unrestricted real host. A timeout/ambiguous launch must not be replayed under a new ID.

The existing Windows protected helper cannot be silently repurposed or modified to accept arbitrary commands. Design and install a distinct, independently reviewed privileged implementation.

## 4. Session grant and lifecycle

A grant binds, at minimum:
- issuer identity and revocation epoch;
- authenticated operator identity and concrete delegated authority reference;
- exact enrolled host key/fingerprint, OS and local protected agent instance;
- unique session UUID, per-command correlation and anti-replay nonce sequence;
- fixed privilege envelope, maximum session duration and absolute expiry;
- concurrency and rate/bandwidth budget;
- explicit audit/sensitive-output classification policy;
- revocation/stop contact and rollback/resume conditions.

The protected host agent independently checks signature/MAC, audience, clock window, local authorization policy and current revocation epoch on **every** command, even after a session was opened. The remote transport/controller must not be trusted to validate its own grant.

Proposed initial bounds for an isolated synthetic canary: at most one FULL_ADMIN session per host, at most 5 minutes, at most one active command in that session, bounded streams, and no renewal. These are candidate limits for security review, not arbitrary permanent product limits.

Grant expiry, revocation, disconnect or conflicting session MUST refuse new commands and trigger host-owned process containment/drain verification. A mere shell exit or command timeout is not completion: enforce and inspect descendants, services and scheduled jobs as described in Gate A3 below. Block new privileged grants until the host proves the previous session clean or enters quarantine. Do not claim irreversible system mutations can always be undone or call a forced kill a graceful rollback.

## 5. Real operations inside the admitted session

The Commander is intended to expose:
- typed host/session enumeration, open, inspect, revoke and close;
- interactive or one-shot command execution from independently approved immutable batches with bounded stdin/stdout/stderr and exit-state correlation; **raw unrestricted console streams remain owner-only**, while model tools receive separately reviewed fixed-schema non-secret results;
- constrained file read/write/edit/search and hash-verified transfers (path restrictions depend on admitted privilege envelope);
- processes, services, system health and owner-authorized machine maintenance;
- optional OS GUI interaction later as a separately reviewed adapter.

FULL_ADMIN-UNRESTRICTED preserves arbitrary owner-authorized administrative commands **after** the specially accepted host/session grant; do not reduce the eventual product to fixed strings. Guardrails include signed real-host risk acceptance, verified owner presence, explicit high-impact intent gates, TTL, target/issuer identity, collision control, audit and revocation, **not guaranteed containment of arbitrary hostile root code**. FULL_ADMIN-CONFINED admits only the reviewed workload/classes enforceable in the externally isolated disposable VM and cannot be mistaken for unrestricted production capability.

However, a model can be induced by untrusted page/tool/agent text to issue a dangerous command. Any command offered by a ChatGPT model is an untrusted proposal until the owner/delegated action policy permits it. Model-driven full-admin use requires a reviewed confirmation/allowance policy for high-impact targets and cannot silently override existing consequential gates.

A command that timed out or lost connection has an AMBIGUOUS execution result, not safe-to-retry. No automatic replay of a potentially mutating shell command. Each command uses a single unique idempotency identity with protected local readback. In **CONFINED** mode the command admission gate matches the signed activity/egress class against trusted source and an outside-privilege boundary **before** a command starts; unknown requests fail closed. In **UNRESTRICTED** mode the actual pre-spawn executable bytes/arguments must match a separately signed immutable owner batch (Gate A1b), and host/mode/risk/high-impact decision gates still apply. This binds the submitted command identity, **not** arbitrary script side-effects: its possible egress/secrets behavior cannot be exhaustively classified or prevented by a same-privilege parser. Never infer safety from stdout, exit code or model rationale.

## 6. Secret and sensitive-output boundary

No reusable privileged credential, private key or administrator password may be **deliberately disclosed** through model-visible tools, command arguments, GitHub, chat logs or unencrypted output. This is a **model-output transport admission rule**, not a claim that unrestricted root/Admin shell execution itself prevents reading or egress of host secrets.

Arbitrary Administrator/root commands **can** read private secrets and send them to stdout/stderr (including encoded, split or binary values); pattern-based redaction, an LLM classifier or command-intent review **cannot guarantee** that arbitrary output is non-sensitive. Therefore the first accepted Commander connector and source proofs enforce:

- **Default deny of raw UNRESTRICTED output to the model:** raw stdout/stderr, streamed chunks, binary payloads, files, exception traces, child-process output, copied logs and arbitrary terminal transcripts go only to a separately protected **owner-visible local terminal/view**, never directly into ChatGPT plugin results, agent memory, relay or GitHub. Owner-only output is still sensitive and requires protected retention/access controls.
- Model-visible results are exclusively **trusted fixed-schema, allowlisted non-secret projections** (for example validated command state, exit category, bounded duration, process count and approved health category), produced by the protected adapter rather than parsed from attacker-controlled shell output. Unknown schema/value, unexpected free-form text, classifier uncertainty or unavailable output gate => `MODEL_OUTPUT_BLOCKED` and no stream; neither `isError` nor diagnostics may echo raw output. Content hashes and status counts are not automatically safe for regulated/customer contexts.
- The connector must block incremental chunks **before** emission; retrospective redaction is insufficient. No raw output copy through tool errors, telemetry, audit-export, notifications, retries or group messages. A separate future raw-to-model feature would require a distinct owner-visible **data-release risk decision and independent security acceptance**; that mode cannot simultaneously promise never to leak credentials, so it is **not authorized** by this Gate A proposal.
- Initial privileged proof uses a secret-free disposable machine/VM, with no real keys, customer material or production mounts in reach; verify deliberate synthetic-secret stdout, Unicode/encoded chunks, binary stderr, nested child output and exception/log mirrors yield only `MODEL_OUTPUT_BLOCKED` to the model connector while owner-only restricted view remains separate.
- Use per-host protected audit with short approved retention, never echo bearer/session secrets, and treat all permitted external program output as **untrusted data**, not instructions or authority. The host's ability to run an approved arbitrary script and its ability to release that script's output to an LLM are **separate authorizations**.

A command that itself exports files/secrets or changes a production system is still consequential. Explicit owner/accepted delegated authority and appropriate data boundary apply even inside a full-admin session.

### Gate A2 — pre-execution data/egress authorization (fixes independent M2)

- **CONFINED proof only:** the protected source-pinned admission service matches a typed reviewed operation and declared arguments against signed owner scope and externally enforced guest/egress controls *before spawn*. A model's "safe" label is untrusted; unknown, non-typed or unanalyzable requests return `UNKNOWN_HIGH_RISK` and **cannot run in CONFINED mode**. This guarantee requires a trusted host/hypervisor boundary outside the guest Admin/root privilege and a denied-packet test; the current nonprivileged synthetic canary is only an ordering proof.
- **UNRESTRICTED real host:** do **not** claim an arbitrary PowerShell/Bash/Python invocation has a complete pre-command secrets/egress classification. Here the admission service verifies the exact host/mode, separately signed owner risk acceptance, time/budget, high-impact intent and accepted batch/policy before launch. An arbitrary command may still exfiltrate or persist; the explicit owner risk decision, not a heuristic parser, is the authority. No automatic fallback from CONFINED failure to unrestricted execution.
- First live proof runs on a **disposable, secret-free host/VM image with external egress blocked outside the command process's authority** and no real credentials, customer data, host SSH keys or connected production mounts. Deny network, outbound file transfers and sensitive path reads by default; only a named test fixture and fixed harmless canary may be accessed.
- **CONFINED negative acceptance tests:** attempts to read a synthetic secret fixture and send it by HTTP/DNS/curl, an encoded variant, or a delegated child must be denied **before process start** by typed admission *or* independently blocked by an external OS/hypervisor network/data boundary with packet/side-effect readback. Tests distinguish pre-spawn refusal from network-isolation enforcement; passing a parser-only refusal does **not** prove the latter. No hidden stdout or simulated 403 is acceptable packet evidence.
- **UNRESTRICTED negative acceptance tests:** absent or forged owner-presence, wrong host/mode/risk, out-of-window grant, unauthorized consequential intent, replayed nonce, revoked signer or unavailable audit must fail closed **before spawn**. Do not use HTTP/DNS denial tests to claim unrestricted admin confinement.
- On an actual owner machine, **full host Administrator/root can alter firewall policy, read protected files, launch services or egress through other processes**. A same-privilege pre-command parser, stdout redactor or environment variable restriction **cannot guarantee confinement** of arbitrary FULL_ADMIN. If no stronger OS/hypervisor boundary exists, require the owner to explicitly accept the named host/session's *unrestricted* egress/secrets risk, or refuse live FULL_ADMIN and use a disposable isolated VM or a narrower MAINTAIN operation. Never advertise complete exfil prevention on an unrestricted production root/admin shell.
- For allowed operations, use enforcement outside the process privilege boundary where possible (dedicated network namespace/host firewalls on a separate trusted control plane, private overlay policy, no production mounts). The first privileged proof must verify **actual network denial**, not merely an expected policy string. Persist only minimal security audit results in approved protected local state; do not capture synthetic secret content into chat/GitHub.

### Gate A3 — privileged descendants, session drainage and quarantine (fixes independent M3)

- The privileged host agent creates a protected **per-session process containment identity**. Windows uses a non-breakaway Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, verifies direct child and descendant membership, and checks Service Control Manager/Task Scheduler for created jobs. Linux uses protected cgroup v2/systemd scope or independently proven equivalent with process-group tracking and descendant readback. **In CONFINED mode**, service/task persistence outside the disposable guest/policy is refused. **In UNRESTRICTED mode**, the owner may deliberately authorize a service/task change as a separately recorded persistent side effect; normal process drain cannot roll it back or prove exhaustive discovery.
- On expiry, revoke, disconnect or owner stop: stop admitting commands; signal/drain all tracked descendants; read back process count, job/scope identity, services/jobs and the **known** file/persistent-side-effect ledger. `DRAINED_VERIFIED` is a **process cleanup assertion only** for the reviewed contained workload; never infer that intentional or unknown persistent Admin/root mutations were rolled back. A separately accepted persistent-effect readback and recovery/owner gate is required before declaring the *host* clean. A child still alive, missing audit/agent, unknown detached service or failed cleanup is `AMBIGUOUS_PRIVILEGED_RESIDUE`, not PASS.
- An ambiguous/failed drain puts that host in **QUARANTINED** and rejects new FULL_ADMIN sessions; a separate trusted owner recovery or independently accepted repair step must inspect the affected processes/services and restore a verified clean state. No blind retry or silent reap that hides evidence.
- **Hard limit:** unrestricted root/Administrator on a normal host can intentionally evade OS containment or create durable services. These protections are provable for the **restricted canary workload**. Broad non-bypassable containment requires a stronger isolation boundary (e.g. a disposable VM/microVM) outside the privileged workload's authority, or an explicit owner risk acceptance; do not promise otherwise.
- Required tests: bounded canary spawns and drains a child on expiration, verified outside its own process; disconnected or failed drain -> QUARANTINED. Deliberate Windows breakaway/service/task creation and Linux daemon/cgroup escape attempt must be rejected in externally CONFINED mode or marked `UNCONTAINED/UNKNOWN_PERSISTENCE` in UNRESTRICTED mode. An **intentional, signed** service installation is tracked as a durable effect, not mislabeled a detached child or cleaned by process kill. A partial side-effect ledger is not an exhaustive security proof.

### Gate A4 — issuer key rotation and clock recovery (fixes independent L1)

- Issuer private signing key is generated/stored only in an approved protected OS/TPM-backed key store; signed public verification keys are pinned by enrolled host with issuer/key ID, validity and rotation generation. No plaintext shared signing secret on the host; no issuer private key in a ChatGPT plugin or agent.
- The agent keeps a **protected monotonic revocation epoch and command nonce journal** with atomic integrity-checked updates, independent from the untrusted chat/relay. A failed journal write, state rollback, cloned node or stale enrolled host key fails closed.
- Require a monotonic local time source where available and **at most 30 seconds** measured wall-clock skew versus a trusted signed time authority. A detected wall-clock rollback, failed attestation, time-source uncertainty or expired signer key means `CLOCK_UNTRUSTED` / no session or command until authenticated time reconciliation.
- Rotate: stage next pinned issuer public key with owner-authenticated policy, increment protected generation/epoch, confirm exact host readback, only then retire old verifier and revoke old grants. Compromise: freeze new sessions, revoke epoch, quarantine affected hosts, re-enroll with out-of-band owner trust, rotate signing and transport keys independently, and require negative tests proving old grants fail even after restart or key rollback.
- A bootstrap/demo may generate ephemeral software-only signing keys **only on a disposable synthetic host**. It is not evidence of production key recovery, secure clock, or physical owner presence.

## 7. Failure and attacker matrix

| Attack / failure | Required property |
| --- | --- |
| Prompt injection in webpage, repository, Slack or mailbox | Untrusted text cannot mint a privileged grant |
| Forged source ChatGPT role or tool argument | No session without cryptographically authenticated delegated operator |
| Stolen one-host key or session token | Cannot administer another host; revoke host epoch locally |
| Replayed grant/command | Single-use nonce and command ID; duplicate returns existing result only |
| Stale/granted-but-revoked session | Agent revalidates every command, refuses after revocation |
| ChatGPT/relay/provider outage | Local CLI uses the **same protected issuer, signer, enrolled host and owner-presence ceremony** as all other paths; no second broker or unsafe offline bypass |
| Owner host offline or role mismatched | HOST_UNAVAILABLE / IDENTITY_MISMATCH, no guessed alias fallback |
| Process still running after timeout | AMBIGUOUS / track and drain or report unresolved; no false success |
| Separate sessions race on service/files | One writer/host or explicit lock; deny untracked conflict |
| Arbitrary Admin/root stdout/stderr contains credentials (including encoded/chunked) | Raw stream cannot reach model-visible transport; fixed-schema allowlist or MODEL_OUTPUT_BLOCKED; raw owner-only channel separately protected |
| Prompt-injection claims owner consent or widens a delegated scope | No out-of-model signed decision: OWNER_AUTH_NOT_PROVEN, no admin grant |
| CONFINED guest tries DNS/HTTP secret exfiltration | Source-pinned typed admission denies unknown request and independently enforced outer network/data boundary blocks packet/file transfer; positive OS evidence required |
| UNRESTRICTED real host can read secrets or egress | Fresh hardware-bound owner risk acceptance for exact host/mode and new consequential intent; never advertise parser-based prevention |
| Detached privileged child survives revocation/disconnect | Host QUARANTINED until descendant/job/service drain is independently verified |
| Issuer signer key compromised, clock rolled back, or epoch journal missing | Freeze sessions and require trusted owner recovery/re-enrollment |
| Malicious local normal-user process | Cannot modify protected agent, trust root, credential store or privileged policy; cannot cause owner decision to be signed by scripting UI/API as the logged-in user |
| Owner signer or issuer offline; trusted time unavailable | No new FULL_ADMIN via CLI or remote; refuse until trusted device/time recovery |
| Revoked node later reappears | Re-enrollment required; no replayed enrollment with same stale key |
| Failed install/upgrade | Exact artifact provenance and rollback, no unrelated host/service mutation |

## 8. Trust-plan independence

No GitHub API, GitHub issue, or Actions schedule is needed for routine command delivery. GitHub can remain version-control history for reviewed source. No ChatGPT Work-mode sessions or Desktop Commander calls should be needed for first-party operational requests after the plugin/tool channel is accepted.

The custom ChatGPT plugin/MCP write-action and idle-chat wake capabilities are **provider-/plan-gated**. Source-level Commander availability must not be misrepresented as guaranteed capability from every ChatGPT account or arbitrary ChatGPT conversation. Keep the CLI and private host control functional when the plugin is unavailable.

## 9. Separate implementation and acceptance gates

**Gate A — architecture:** this contract and an independent security/architecture challenge, including threat-model findings and a frozen trust decision. The GM17 author is not eligible to terminally accept its own design.

**Gate B — synthetic user-mode source:** a stand-alone disposable local CLI + session state machine and harmless file/process/command proof, with synthetic signed decisions, expiry/revoke/replay/collision tests. Require fake-owner-consent, wrong host/mode, unknown typed operation/refused-before-spawn, forged issuer, epoch/clock rollback, **actual signed-batch command/argument/script tamper refusal, unapproved interactive command refusal, default-deny raw model output including encoded/chunked synthetic credential**, and child-process drain/quarantine negatives. This proves **source ordering only**, not external network isolation, genuine owner physical presence or full-admin release. Current draft #215/#217/#219/#221/#222 source improves those proofs but does NOT satisfy production Gate A2/A3/A4 requirements.

**Gate C — Windows CONFINED protected proof:** new reviewed protected service/session helper installed only under a separate consequential owner/security gate on a **secret-free disposable Windows guest**, with owner-signed `FULL_ADMIN-CONFINED` scope and outside-guest confinement, one harmless elevated command, independent denied-packet test, Job Object descendants and clean revoke/drain/quarantine. This does **not** authorize unrestricted execution on the owner's physical workstation. Do not install on the owner's production workstation merely because a synthetic source PR passes.

**Gate D — Linux CONFINED protected proof:** distinct OS-specific root-capable source and disposable **secret-free guest** proof with protected cgroup/process drain, externally enforced network-egress denial, clock/revocation recovery and quarantine negative cases; preserve ChromeOS verified boot, owner login and existing REDRIX isolation boundaries. No assumption that ChromeOS penguin containers can safely prove root host control.

**Gate E — normal ChatGPT Chat connector:** two separately enrolled hosts reachable from an actually supported private plugin/tool connection in ordinary Chat mode; verify authenticated command/result and account/plan controls without Work or Desktop Commander. Must still work locally through CLI during remote outage.

**Gate F — UNRESTRICTED real-host recovery/use:** only after Gates A–E and a **fresh human-verified owner acceptance naming each actual host, unrestricted secrets/egress/persistence risk, recovery plan and accepted work batch**, permit one harmless elevated command, one eligible file edit and one intentionally authorized process/service action. Verify privilege, host identity, **pre-spawn exact executable/batch digest and immutable loaded bytes**, signed intent/batch, **model-output denial versus separately protected owner-only console**, protected journal, session close, expiry refusal, offline/revocation, named persistent effects and rollback/readback. Never assert that process drain alone reverses service/file changes. If owner presence, signer/clock, audit or actual host admission is unavailable, NO_START instead of defaulting to an unrestricted root shell. No customer/regulated data or new variable spend.

### Shared local CLI authority and trusted-time outage (addresses independent L2)

The local CLI is a **second interface, not a second authorization broker**. It submits to the same host-enrolled verifier, pinned independent owner signer, session issuer, protected nonce/revocation journal, owner-presence ceremony and mode policy used by the private connector. It may remain locally usable during **ChatGPT/relay** outages **only if** this protected trust chain and trusted time remain healthy. If the trusted signer/time authority is unavailable or the signer has expired, CLI FULL_ADMIN is **NO_START/CLOCK_UNTRUSTED**, never a separate local-password/OS-user shortcut. OBSERVE diagnostics may remain available where their independent low-privilege policy permits.

The first owner-signer enrollment and future key rotations require explicit out-of-band physical presence and keyed public-pin readback; the acceptance screen must display and bind host, FULL_ADMIN mode, accepted batch/risk digest, max lifetime and egress/secrets exposure. A user-mode ChatGPT/LDW agent process must not be able to manufacture this approval, drive a silently scriptable prompt or access a signer private key.

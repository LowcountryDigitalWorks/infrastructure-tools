## What it proves when hosted CI passes

**Completed disposable cross-version experiment (not a host downgrade):** exact-head hosted workflow `41900822476` ran the same pinned Docker/Chromium/sandbox tests on `ubuntu-22.04` and `ubuntu-24.04`. The former reported `HOST_APPARMOR_RESTRICT_UNPRIV_USERNS=DISABLED`; the latter reported `ENABLED`. Both nested-namespace sets and both real-Chromium trusted synthetic network-negative tests passed, **but strict Chromium failed identically with zygote-related launch refusal on both**. Therefore Ubuntu 24.04's additional AppArmor restriction cannot by itself explain this failure; the shared container/Chromium sandbox path remains unresolved. The temporary two-runner matrix was **removed immediately after this comparison** to avoid recurring extra CI capacity. The mandatory job is back on 24.04. No host AppArmor/kernel/Docker policy, owner machine or production service was changed.

- Runs **real full Chromium (Playwright `channel: 'chromium'` new-headless mode)**, not a headless-shell route mock, inside Docker `--network=none` with immutable image-ID admission, non-root user, read-only rootfs, no mount/host profile/Docker socket, no external ports, no host IPC, no capabilities and bounded resources.
- Browser uses an embedded `127.0.0.1` standard-library HTTP fixture. Positive proof must navigate, fill, click, read DOM and generate screenshot digest with an actual browser.
- The same browser attempts `navigator.sendBeacon`, link `ping`, `fetch(keepalive)`, WebSocket, image resource and Service Worker fetch to a synthetic private **host-side** listener. It also tries a 302 redirect off-guest. A direct Node TCP attempt inside the same guest is a baseline; failed host TCP is mandatory.
- Host listener is bound **only** to Docker's private bridge address on the ephemeral disposable GitHub runner. The host first proves the listener actually receives its own positive connection, then asserts **zero additional connections** after guest/browser exit. This host-side readback—not browser interception counts alone—is the negative control.
- Guest requires `chromiumSandbox: true` for the non-root browser. **No automatic `--no-sandbox` fallback**. The first hosted attempt failed at BROWSER_LAUNCH under Docker default seccomp; the exact kernel/OCI cause was **not proven** from redacted errors. Even with the upstream policy added, strict Chromium still returns BROWSER_LAUNCH NO_START on hosted Ubuntu; that failure remains a release hold. A separate CI-only disposable guest `unshare --user --map-root-user true` probe now reports AVAILABLE/UNAVAILABLE without changing host policy, and does **not** attest actual Chromium sandbox isolation. This candidate now vendors the **exact upstream Playwright** [`utils/docker/seccomp_profile.json`](https://github.com/microsoft/playwright/blob/1af60d94ac714d4007828bafa02b0f1cbd8646b9/utils/docker/seccomp_profile.json), Git blob `fddc05fb520affb145404e6f6f647ca96af8087d`; this is the official default-derived seccomp policy with additional `clone`/`setns`/`unshare` syscall admission. The host checks the exact Git blob before every Docker launch and supplies it as a Docker **seccomp profile**, never `seccomp=unconfined`. The Apache-2.0 notice is preserved in `UPSTREAM_LICENSE.txt`. A Docker engine, user namespace or Chromium incompatibility still returns NO_START, not a fabricated PASS. `sandbox_requested: true` is a command-contract check, not full kernel attestation of a browser sandbox. Browser sandbox still needs independent audit.
- It uses Microsoft's published [Playwright 1.64.1 Ubuntu Noble image](https://mcr.microsoft.com/en-us/artifact/mar/playwright/tag/v1.64.1-noble) pinned to OCI index `sha256:2f05f8a734509a7b3f26a912639488ee08f58a7b292d14d62271bcff9038768f`; matching JavaScript package `playwright@1.64.1` is installed in the **build phase** using public npm. ## Exact code boundaries

- `probe.js`: only synthetic local pages, ephemeral guest-side HTTP service and fixed off-guest attempt vectors; no owner login, profile, credentials, real target URLs, persistent listener or model-supplied command.
- **Diagnostic provenance correction:** earlier direct subprocess `GUEST_BROWSER_LAUNCH_DIRECT_ZYGOTE` categories were generated from `chromium.executablePath()`, which is not guaranteed to be the same full-Chromium executable selected by `chromium.launch({channel:"chromium"})`. Those earlier zygote labels therefore do **not** establish the actual strict-launch cause. The separate direct subprocess has been removed. New fixed error categories are parsed only from the actual Playwright launch exception. Raw browser logs/command lines are never published.
- **Syscall readback evidence:** exact-head hosted run `41901615869` showed `GUEST_CLONE3_NULL_PROBE=UNSUPPORTED_ENOSYS`; this is the compatibility errno used by Docker and Chromium to permit fallback to `clone`, **not evidence of a `clone3` seccomp denial**. No `clone3` allowlist expansion or seccomp policy relaxation is authorized.
- `host_proof.py` also uses CI-only `--host-policy-readback` for fixed `ENABLED`/`DISABLED` AppArmor and userns statuses, and `--clone3-null-check` for a deliberately invalid `clone3` syscall in a nonroot `--network=none` guest. The latter distinguishes seccomp/kernel errno categories without actually cloning a process or changing host policy. **Neither diagnostic attests that Chromium's layered sandbox launched.** Raw host/kernel errors and container stderr remain withheld.
- `host_proof.py` offers `--userns-check` on GitHub Actions **only**: three bounded nonroot guest `unshare` probes (user, nested user+PID, nested user+PID+network) under the same pinned seccomp and `--network=none` policy, returning fixed capability statuses. They **all returned AVAILABLE** on the disposable runner while strict Chromium still exited, so a general absence of nested namespaces is not the demonstrated root cause. No host security policy is changed. These probes do not attest the browser sandbox.
- `host_proof.py`: fixed Docker flags, exact image SHA and cryptographically random per-run **container name/nonce label**; uses `docker container create`, identity-readback, `start --attach` and `rm --force` **only for its own nonce-bound guest**, then requires absence with a responsive daemon before it reports cleanup verified, including on launch failure/CLI timeout. Foreign/misbound containers are never deleted. Tests simulate timeout, residue and label spoofing; create-time ambiguity always fails. It also verifies a short-lived synthetic Docker-bridge host listener and no extra guest connections. Raw Chromium stderr, page content and attempted addresses are never emitted.
- `Dockerfile`: pinned upstream version+digest, non-root uid 10001, no browser package at runtime download.
- `test_host_proof.py`: strict command admission, mandatory vector set and evidence-schema negatives.
- `.github/workflows/browser-chromium-isolated.yml`: disposable Ubuntu PR-only job, normal contents:read GitHub token, public base-image download and source build.

**Two explicitly separate CI modes, never an automatic fallback:** strict production-oriented *test* mode requests `chromiumSandbox:true` and must PASS before the strict job can become green; an additional **CI-only `--trusted-synthetic-only` diagnostic** requests `chromiumSandbox:false` solely for the trusted, static test fixture. This second mode retains Docker `--network=none`, non-root UID and all fixed host isolation flags, but reports `TRUSTED_SYNTHETIC_NO_CHROMIUM_SANDBOX`, and **cannot satisfy the sandbox security gate**. CI runs the diagnostic first, then the strict gate; strict failure leaves the overall workflow **FAILED** even if the diagnostic passes. No real external website is visited in either mode, no user data/browser profile is mounted, and the diagnostic cannot be selected by model tool input or used outside GitHub Actions. **Only strict success qualifies as full proposed test PASS**, and even that does not authorize production untrusted browsing.

## Exact TEMP experiment

The only new executable is host-agent/deploy/tests/Test-RedrixLdwAncestorIdentityTemp.ps1 in an ordinary hosted Windows PowerShell 5.1 x64 job. It has NO arguments and writes/deletes only its newly created GUID-named directory under runner TEMP, explicitly refusing the OS ProgramData tree. It never imports or runs production privileged source.

The fixture uses Win32 CreateFileW FILE_FLAG_BACKUP_SEMANTICS + FILE_FLAG_OPEN_REPARSE_POINT, share READ|WRITE but deliberately NOT DELETE, and two **distinguished access classes**. An attribute-only `FILE_READ_ATTRIBUTES` handle on a disposable control sibling is observed with a rename attempt; the outcome is recorded as `A0_TEMP_ATTRIBUTE_ONLY_RENAME=ALLOWED|DENIED`, not treated as a security result. Microsoft documents that access requests for attributes are not affected by normal sharing mode. Separately, it opens the synthetic root/ancestor/child and an **isolated ancestor** with `GENERIC_READ` substantive access and no delete sharing. It then independently attempts renaming (1) the held child, (2) the isolated held ancestor, and (3) **the actual synthetic nested ancestor containing the still-open child**, recording all outcomes before any security assertion can abort the test. Each emits a specific `A0_TEMP_GENERIC_READ_*_RENAME` marker with its Windows HRESULT. The test requires all THREE moves to be denied with **only** Windows ERROR_ACCESS_DENIED (5) or ERROR_SHARING_VIOLATION (32), plus stable original paths and same-handle object identities; an unrelated IOException or successful rename fails the fixture. The nested experiment holds both ancestor and descendant handles, so the denial is **not uniquely attributed** to either handle. Only those strict conditions may yield `REDRIX_A0_ANCESTOR_IDENTITY_TEMP=PASS`. `GetFileInformationByHandleEx(FileIdInfo)` supplies volume+128-bit object identities; `FileAttributeTagInfo` checks reparse, `GetFinalPathNameByHandleW` checks the synthetic child path, independent opens must match their object, and an unheld control rename must succeed.

## ORCH13 additional hostile TEMP negative tests (Nov 17, 2026)

An independent feasibility challenge of #186 found that existing rename/delete-capable open handles are not ruled out merely because a **later** access handle uses `GENERIC_READ` and refuses `FILE_SHARE_DELETE`. This draft revision deliberately tests both distinct counterexamples in **disposable TEMP**:

1. Open a fixed sibling directory first with `GENERIC_READ|DELETE` access and full sharing; then attempt the proposed stronger `GENERIC_READ` **no-delete-sharing** open. It MUST fail with exactly `ERROR_SHARING_VIOLATION (32)`, never return a usable handle or imply parent-chain trust. Only the fixed TEMP sibling is accessed. A pre-existing DELETE-capable process is not assumed absent on real LDW01.
2. When the weak `FILE_READ_ATTRIBUTES` control rename succeeds, inspect `GetFinalPathNameByHandleW` on the *same existing handle*; it must now name the moved object. Re-create the old disposable path, open it independently and require that its `FileIdInfo` differs from the still-open old handle. This demonstrates that a stable file ID does **not** imply a stable old pathname. The weak control is never promoted into an authorization path.

These tests are added to the existing no-argument PowerShell 5.1 x64 TEMP-only fixture under the same #324 draft; no production mutator or host ProgramData operation.
